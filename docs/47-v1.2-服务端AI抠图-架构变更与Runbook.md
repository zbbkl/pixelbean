# 47 · 服务端 AI 抠图（架构变更 · 决策与 Runbook）

> 触发：项目所有者提出「模型既然在我们服务器上，为什么还要用户自己下载？」并拍板**改为服务端推理**。
> 取代 [`docs/45`](45-v1.2-可选AI抠图任务书.md) §6b/§12.3 的「浏览器内 ONNX + 自托管模型」方案；浏览器内推理的实现已移除。
> **本变更同时修改了产品承诺**：此前 README/`docs/08` 写的是「图片不会上传到任何服务器」——开启 AI 抠图后**图片会上传**，见 §5。

---

## 0. 一句话结论

AI 抠图从「用户浏览器下载 44MB 模型 + 本地 WASM 推理」改为「**图片发到自家服务器算，返回掩码**」：
**用户零下载**，服务器用质量更好的 fp32 模型，移动端不吃算力。
代价是**图片会上传到服务器**（服务端不落盘、不记录像素），并新增一个常驻服务。

实测（线上 39.104.21.103，2 核 / 3.4GB）：

| 指标 | 改前（浏览器内推理） | 改后（服务端推理） |
|---|---|---|
| 用户首次等待 | **337 秒**（44MB @ 该机上行 142KB/s，HTTP 下**每次**都要重下） | **14 秒**（零下载） |
| 用户端体积 | 44.2MB 模型 + ORT 运行时（数 MB） | **0** |
| 模型质量 | ISNet-int8（量化，170.4→44.2MB） | **u2net fp32（未量化，167.8MB，存在服务器上）** |
| 出图 | 2610 → 1462 格 | 2610 → **1457 格**（两个模型逐像素 IoU 0.9873） |
| 图片隐私 | 不出设备 | **上传到服务器**（不落盘） |
| 服务器成本 | 0 | 2 核机器上约 3.6s/张（高质量档）、1.45s/张（快速档） |

---

## 1. 为什么换

1. **用户下载这条路在该部署下不可用**：实测该机上行 **142 KB/s** ⇒ 44MB 首下约 5 分钟；而且 HTTP 非安全上下文下 `caches` 与 `crypto.subtle` 都不可用（详见 `docs/08` §7.4），导致**每次都重下**。
2. **服务端推理顺带解锁更好质量**：不用再为体积妥协，直接用 **u2net fp32**（与 ISNet 逐像素 IoU 0.9873、面积差 0.6%）；且 u2net 是 **320² 输入**，比 ISNet 的 1024² 省算力得多——这对 2 核机器是决定性的。
3. **移动端友好**：手机不用下 44MB、不用跑 1024² 的 WASM 推理。

## 2. 模型选型（服务器实测，2 核）

| 档位 | 模型 | 体积(磁盘) | 热推理 | 内存 RSS | 掩码面积 | 对 ISNet 的 IoU |
|---|---|---|---|---|---|---|
| **高质量（默认）** | u2net fp32 | 167.8MB | **3.64s** | 792MB | 803,266px (51.1%) | ~0.99 |
| **快速** | u2netp | 4.36MB | **1.45s** | 389MB | 794,385px (50.5%) | 0.979 |
| ~~不采用~~ | ~~ISNet-int8@1024~~ | 44.2MB | 预计 5–15s | — | 803,579px | 1.0（基准） |

> ISNet 在 2 核上太慢（1024² 输入），且其质量优势（相对 u2net）只有 0.6% 的边界差 —— 服务端场景下不划算。
> **同一时刻只保留一个模型会话（LRU=1）**，因此内存恒定，两个档位可并存。

## 3. 架构与协议

```
浏览器                                   nginx (:80 /pixelbean/)                    pixelbean-ai (:8790, 仅本机)
  ├─ 解码图片、缩放到模型输入尺寸(320²)  ─┐
  ├─ POST /pixelbean/api/mask?model=&size= ─┼─► proxy_pass http://127.0.0.1:8790/ ─► 归一化 → ONNX(WASM,2线程) → 阈值
  └─ 收到 size² 的 0/1 掩码字节 ◄──────────┴───────────────────────────────────────┘
       └─ 走既有管线：extractSubjectFromAIMask → 同一道可靠度门 → despill → 像素化
```

**关键设计：服务端不做图像编解码**。客户端本来就已经把像素解码好了，所以直接把**缩放后的原始 RGBA** 发上去，
服务端只做「归一化 + 推理 + 阈值」，返回 `size²` 的 0/1 字节。
好处：服务器**不需要 sharp/jpeg-js 之类的图像库**（这台机器 Docker Hub 不可达、onnxruntime-node 的原生二进制也下不下来，
只能用 **onnxruntime-web 的 WASM 后端**——纯 JS + wasm，npm 可直接安装）。

### 3.1 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/pixelbean/api/mask?model=<id>&size=<n>` | body = RGBA 原始字节（`size²×4`）→ 200 = 掩码字节（`size²`，0/1） |
| `GET` | `/pixelbean/api/health` | `{ ok, model, served, loaded, switchAllowed, modelsOnDisk }`（`served` 只列**实际服务**的档位） |

错误码：`400` 参数错（未知模型/尺寸不符/RGBA 长度不符）、`413` 过大、`429` 单 IP 限流、`503` 忙（并发 1 + 队列 4）。

### 3.2 工程约束（为这台 2 核 / 3.4GB 且跑着别的服务而定）

- 并发上限 **1**、队列上限 **4**，超限立即 503（宁可快速失败，不拖垮同机的 mingli / guantou / llm-proxy）；
- 单 IP **40 次/分钟**限流；
- systemd 单元设 `MemoryMax=1300M`、`CPUQuota=180%`；
- **常驻只加载一个模型**（`MODEL_ID`，默认 `u2net-quality`）：运行时不切换，请求其它 id 返回 400（原因见 §6.1）；
- 加了 2GB `/swapfile` + `vm.swappiness=10` 作为兜底（正常路径用不到，只为极端情况留回旋余地）；
- **不落盘**：像素只在内存中处理，请求结束即释放；日志只记 `路径/状态/耗时/模型/尺寸`，**不记像素**。

### 部署步骤（已在线上执行）

```bash
# 服务器
mkdir -p /opt/pixelbean-ai/models && cd /opt/pixelbean-ai
npm init -y && npm i onnxruntime-web --ignore-scripts      # 纯 JS/wasm，无原生依赖
curl -sSL -o models/u2net.onnx   https://hf-mirror.com/tomjackson2023/rembg/resolve/main/u2net.onnx
curl -sSL -o models/u2netp.onnx  https://hf-mirror.com/tomjackson2023/rembg/resolve/main/u2netp.onnx
# 装服务（server.mjs + systemd 单元）
systemctl daemon-reload && systemctl enable --now pixelbean-ai
# nginx：在 /pixelbean/ 之前插入 location /pixelbean/api/（先备份配置，再 nginx -t，最后 reload）
# 前端：npm run build → 上传 dist（**不再包含模型**，站点因此省下约 50MB）
```

> 注意：`hf-mirror.com` 从服务器可达（`huggingface.co`/`github.com` 不可达），所以在服务器上直接取权重比从本地上传快得多。

### 6.1 OOM 事故与修复（2026-09，本机实测）

**起因**：最初为支持两个档位（高质量 / 快速）实现了「LRU=1 换入换出」，以为同一时刻只有一个会话、内存就恒定。

**实测**：每切换一次内存涨 100~200MB —— onnxruntime-web 的旧会话 WASM 堆并没有真正释放。

| 事件 | `MemoryCurrent` | cgroup 峰值 |
|---|---|---|
| 启动 + 首次推理 | 884MB | — |
| 切到另一档位 ×1 | 957MB | — |
| 再切 ×3（累计 5 次切换） | 1133MB | **1266MB** |

上限只有 1363MB（`MemoryMax=1300M`）⇒ 再切几次必然 OOM-kill；期间整机 `available` 一度掉到 **623MB**（同机还有 mysqld 486MB、hermes 273MB 等）。

**修复**：① 默认**锁定单模型**，请求别的 id 明确返回 `400`（不再偷偷加载第二份）；② 释放旧会话时显式调用 `session.release?.()`；③ 加 2GB `/swapfile` + `vm.swappiness=10`；④ 前端同步改为**单档位**（不再显示会 400 的选择器）。

**修复后实测**：连续 8 次同一模型，cgroup 峰值**恒定 940MB**（`current` 782→796MB），整机 `available` 回升 1180MB，swap 使用 0。仅剩约 +1.7MB/次 的轻微漂移（JS 堆惰性回收），峰值不涨 —— 若长期运行要更保险，可给单元加 `RuntimeMaxSec` 定期重启。

## 8. 诚实边界

- **14 秒并不是"很快"**：它包含「我家宽带上行 410KB → 服务器」「2 核推理 3.6s」「掩码回传」与前端转换；换更快网络/更好机器会明显改善。第二次实测出现 33s，波动来自服务器负载（同机还跑着别的服务）。
- **服务器只有 2 核 / 3.4GB**：并发 1 已是保守上限；若要多用户同时用，需要升配或加队列/云函数。**内存是这条路线上最脆弱的一环**（见 §6.1：换模型会漏 WASM 堆，已用「锁定单模型 + swap 兜底」处理）。
- **隐私**：虽然服务端不落盘，但图片确实经过了我们的服务器与公网（当前是 **HTTP 明文**）。若要在这条路上继续，**强烈建议配 HTTPS**。
- **u2net 权重许可**：U-2-Net = Apache-2.0（GitHub API 实取，见 `docs/45` §1）；`docs/45` 的许可核证结论仍然适用。
