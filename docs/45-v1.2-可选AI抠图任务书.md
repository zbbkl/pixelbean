# 45 · v1.2 可选 AI 抠图（浏览器内 ONNX）任务书

> 流程：DeepSeek（规格）→ **Codex（实现）** → Claude Code（复核）。
> 承接：[`docs/44`](44-v1.2-去背景A+B修订自测报告.md) §12（权威样例实测：确定性路线对该类图不可行）与 §13.4（遗留的产品决策）。
> 决策：项目所有者选择 **路线 A —— 浏览器内跑小模型，做成可选增强**（非默认依赖、不改变现默认行为）。
> **红线（沿用 docs/43 §0，且对 AI 路径同样生效）**：任何情况下**不得吞主体/产空图纸**；AI 未下载、离线、推理失败、或结果不可信 → 一律落回现有行为（含 docs/44 §13.3 的提示）。
> 纪律（沿用 docs/00 / docs/42 §5）：**只借鉴思路不抄受限代码**；AGPL/GPL/无证/非商用权重一律不得引入。

## 0. 一句话方案

在现有**确定性**去背景（默认关闭、可靠度兜底）之外，另加一个**默认关闭、按需下载模型**的「AI 抠图（增强）」入口：模型在**本机浏览器内**推理（图片不出设备），输出的**软 alpha** 接进现有的 `extractSubject` 下游契约（掩码 → 主体盒 contain → 像素化 → 匹配 → `clearBackgroundCells`），并**照样过同一道可靠度门**。

## 2. 模型选型（两选一，建议先做 A1）

| | **A1 · U-2-Net / u2netp** | **A2 · MobileSAM** |
|---|---|---|
| 性质 | 显著性目标检测，**全自动**（无需用户操作） | **可提示**分割（需用户点一下主体或拉一个框） |
| 许可 | Apache-2.0 ✅ | Apache-2.0 ✅ |
| 体积 | u2netp ≈ 4.7MB（轻量）/ u2net ≈ 176MB | 编码器 5M 参数（ONNX 量化后约 10–40MB 量级） |
| 输出 | 显著图（近似 alpha） | 精确掩码（对「点中的物体」） |
| 对 docs/44 §12 那张兔子图 | 靠**语义**判前景，理论上正是破局点（待实测） | 更强：用户一点即给出该物体轮廓 |
| 代价 | 效果未知（须实测）；对「多个显著物」可能选错主体 | 需要新增交互（点选/框选）+ 更复杂的后处理（框内多掩码选优） |
| 建议 | **先做 A1**（改动最小、无交互），效果不达标再上 A2 | 备选增强 |

> 注：`@bunnio/rembg-web` 一类「rembg 的浏览器 TS 移植」可直接跑 u2net，但**引入第三方包需你单独批准**（见 §6 依赖策略）。默认按「自写 ONNX 包装 + Apache-2.0 权重」设计。

## 3. 架构设计

```
用户勾选「AI 抠图（增强）」
  → 首次：下载权重（带进度、可取消、写入 Cache Storage + 校验 sha256）
  → 推理（放在现有 convert.worker 或独立 ai.worker，避免阻塞主线程）
  → 软 alpha (0..255)
  → 阈值化 + 复用现有 refineMaskGuided / fillSmallHoles / dropTinyIslands
  → subjectMetrics → **同一道可靠度门**（ratio / largestComponent / bbox）
  → 通过：等价于现有 'applied'；不通过：落回 fallback（并复用 §13.3 的提示）
```

**关键设计决定（请审）**：

1. **AI 结果照样过可靠度门**（`SUBJECT_RATIO_MIN / COMPONENT_MIN / BBOX_MAX`）——红线对两条路径一致，绝不因为"用了 AI"就免检。
2. **AI 与确定性路径互斥**：勾了 AI 就不再跑 `floodColorBackground`（语义掩码不需要颜色判据），但共用下游（contain / 掩码降采样 / `clearBackgroundCells` / 统计）。
3. **对外的 `Pattern.backgroundRemoval` 扩展为三态**：`'applied' | 'fallback' | 'applied-ai'`（增量字段，关闭态仍不带）。
4. **模型不入库**：权重不进 git；`public/` 只放运行时壳或干脆走 CDN（见 §6）。图片**全程不出设备**（相对路线 B 的核心优势）。
5. **现有默认行为零变化**：不勾 = 与今天逐格一致（这条要有回归断言）。

## 5. 验收门禁（G1–G7 的对应改法）

**沿用现有 G1–G7 不变**（默认关态），另加**AI 路径专项门禁**：

| 编号 | 判据 | 样例 |
|---|---|---|
| **GA1** | AI 路径在**权威样例**上 `reliable=true` 且 `subjectRatio ∈ [0.2, 0.75]`、`comp > 0.9` | `tests/fixtures/rabbit-soft.png`（+ 全分辨率 `rabbit-source.jpg` 本地跑） |
| **GA2** | 主体完整性：mask 覆盖主体核心（用 docs/41 §G2 的「bbox 上部 1/3 覆盖率 > 0.8」口径）+ **目检无缺块** | 同上 + 目检证据 PNG |
| **GA3** | **不回退也要过**：若 AI 结果不可信 → 必须落回 fallback（禁止"带病出图"） | 纯色图 / 极端图 |
| **GA4** | 关闭/未下载/离线三种情况下，输出与今天**逐格一致** | 5 图 × 3 配置 hash 对照 |
| **GA5** | 体积与首屏：未启用 AI 时**首屏 JS 体积增量 = 0**（动态 import）；权重不计入首屏 | `vite build` 产物对照 |
| **GA6** | 许可与出处：模型/运行时的许可文本与 sha256 记入 `data/provenance/README.md` | 人工核对 |
| **GA7** | 真实浏览器：下载 → 推理 → 出图 → 导出全链路无错（扩展现有 `run.mjs`） | Playwright 21 项 + AI 专项 |

**GA1/GA2 是这次的核心**：如果 AI 路径在 `rabbit-soft.png` 上也过不了，那么**这条路同样失败**，应如实回报而不是硬调（docs/41 §6 的纪律）。

## 6. 依赖与体积策略（需你拍板一处）

| 方案 | 说明 | 取舍 |
|---|---|---|
| **6a. 自托管**：`onnxruntime-web` 放 `public/ort/`，权重放 `public/models/`（或对象存储） | 离线可用、无第三方运行时请求、CSP 友好 | 部署包变大（ORT 数 MB + 权重 5–40MB）；若权重入 `public/` 需确认"入库 vs 部署上传" |
| **6b. 动态 CDN**：运行时 `import()` 固定版本 CDN（带 SRI/pin） | 仓库/部署包不变 | 依赖第三方可用性；需 CSP 放行；供应链风险 |

**建议 6b + sha256 校验 + 本地缓存**（仓库保持干净，下载一次后离线可用）。`package.json` 是否新增 `onnxruntime-web` 依赖：**建议不加**（走 6b 动态加载），以免违反既有「零新增依赖」纪律；若你希望离线自托管则必须加依赖（需你批准）。

## 8. 风险与待定（实现前先看这里）

1. **效果未知（最大风险）**：U-2-Net 这类显著性模型对「白底白兔」是否真能给出完整主体，**只能用权威样例实测**。若不行 → 换 MobileSAM（A2，需交互）或如实回报"浏览器内可商用模型都不达标"。
2. **权重许可仍需单独核**（§1 的 ⚠️）：代码 Apache-2.0 不代表权重亦然。
3. **体积与首屏**：ORT + 权重会显著增加"首次下载"；必须动态加载，否则直接违反项目的首屏纪律。
4. **移动端能力**：iOS Safari 的 WASM 内存上限与 WebGPU 缺失；需真机或模拟实测，必要时降级到小输入分辨率。
5. **推理耗时**：1104×1424 直接跑可能数秒；可先降采样推理再上采样掩码（**注意这会影响软边精度**，需实测）。
6. **阴影处理预期**：模型可能把接触阴影一起判进主体或判出去——这属于**产品预期问题**，需要你确认"要不要保留地面阴影"。
7. **CSP / 跨域**：静态部署若禁用了 `wasm-unsafe-eval` 或第三方连接，需同步调整部署配置（`docs/08` 部署指南）。

## 9. 建议的实施顺序（每步可独立回退）

## 11. S1 实测结论（已完成，2026-09）

> S1 是 §9 的**廉价否决点**：不写产品代码，只回答「掩码是否完整覆盖主体」。实现在
> `tests/acceptance/ai-spike.test.ts`（未装 onnxruntime-node 或缺权重时自动 skip）。
> **偏差**：S1 脚本落在 `tests/acceptance/` 而非本文原写的 `.tools/`——因为它需要复用
> TS 版 PNG 解码器（`tests/support/png.ts`）。权重与量化产物仍在 `.tools/ai-spike/`（本地，不入库）。

### 11.1 三个模型（均已跑通，权威样例 1104×1424）

| 模型 | 体积 | 输入 | 归一化 | 掩码 | 推理(本机 CPU) |
|---|---|---|---|---|---|
| u2netp | **4.4MB** | 320 | ImageNet | 794,385px (50.5%) | 105ms |
| u2net | 167.8MB | 320 | ImageNet | 803,266px (51.1%) | 214ms |
| isnet-general-use | 170.4MB | **1024** | mean0.5/std1 | 803,854px (51.1%) | 623ms |
| **isnet int8**（我们量化） | **44.2MB** | 1024 | 同上 | 803,579px (51.1%) | 1130ms |

**关键结论**：
1. **大模型不值**：u2net(167.8MB) 相对 u2netp(4.4MB) 只多 1.1% 面积，逐像素近乎相同。
2. **架构差异也很小**：u2net 与 isnet 的**掩码面积**为 803,266px vs 803,854px（差 0.07%）；而**逐像素 IoU 0.979** 是
   **u2netp 与 isnet** 之间测得的。
   > ⚠️ **更正（2026-09）**：初版这句话把「面积差」与「IoU」混写在一起，且当时**并未测过 u2net 与 isnet 的逐像素 IoU**。
   > 经项目所有者指出「ISNet 也是量化版，拿 u2net 未量化版比体积不公平」，已在 §11.7 补测并更正结论。
3. **ISNet 是目检最完整的一版**（项目所有者判定），且**int8 量化后质量几乎不变**：IoU **0.9994**、面积差 0.03%
   ⇒ **170.4MB → 44.2MB，质量不变**，这是网页产品可接受的档位（量化脚本 `.tools/ai-spike/quantize.py`，
   `onnxruntime.quantization.quantize_dynamic(QUInt8)`，2.8s 复现）。
4. **倾向结论：主档用 ISNet-int8（44.2MB）；u2netp（4.4MB）作为轻量档备选。**

### 11.2 被实测否掉的方案（省得再走一遍）

| 方案 | 结果 |
|---|---|
| 提到 640/960 输入 | ❌ ONNX 导出是**固定输入尺寸**，喂 640 被 ORT 直接拒绝 |
| 按 bbox 裁出主体再缩到 320 | ❌ 第一趟 bbox 已近整幅（缩放比 1.0×），**没有可放大的余量** |
| 2×2 分块推理 | ❌ 更差（24.9%，主体中心直接丢失）——显著性模型需要**看到整个物体**的上下文 |
| 膨胀模仿 ISNet 的"更完整" | ❌ IoU 反而从 0.9792 降到 0.956（整体虚胖），漏区只补回 42% |
| 引导滤波（现有 `refineMaskGuided`）补全 | ❌ 只补回 7.0% |
| isnet 用 ImageNet 归一化 | ❌ 输出一片散点（0.4%）——**每个模型的预处理参数必须单独配** |

### 11.3 缺块的性质（已定量）

u2netp 相对 ISNet 漏掉的 **13,144px 全部在轮廓边界**（内部洞 0 个），约等于沿周长 1.8px 宽的一圈；
ISNet 的边界略"胖"且更贴合。**这不是漏结构，而是边界完整度差异** —— 与目检结论一致。

### 11.4 模型托管的地域事实（影响 §6b 选型）

本机实测：`huggingface.co` 与 `github.com` releases **不可达**；`hf-mirror.com`、`cdn.jsdelivr.net`、
`registry.npmjs.org`、`raw.githubusercontent.com` **可达**。⇒ 上线时必须选定目标用户可达的 CDN 或自托管，
不能默认 HF/GitHub 能下。

### 11.5 许可链仍需固化（GA6）

权重取自 HF 镜像 `tomjackson2023/rembg`，但**该镜像未声明 license**（字段为空）。
正式采用前必须：① 回到原始仓库（U-2-Net = Apache-2.0 / DIS = 待核）读 **LICENSE 原文**；
② 固定制品 sha256（见下）；③ 把许可文本、出处、量化脚本一并记入 `data/provenance/README.md`。

### 11.6 S1 判定

**GO**（继续 A1 路线）：AI 掩码 `subjectRatio=0.511`、bbox 占比 `0.772` → 按现有可靠度门会判
`reliable=true`；而确定性路线在**同一张图**上从未判过可信。剩余待办：① 模型档位最终确认；
② 接触阴影是否补回；③ 进入 S2（worker 接入 + 后处理 + GA1–GA3）。

**已确认档位（2026-09）**：**主档 = ISNet-int8（44.2MB）**（此判定在「浏览器内推理、用户需下载模型」的前提下作出；架构改为服务端推理后已失去意义，见 §11.7 与 `docs/47`）。

### 11.7 更正：u2net 同样可以量化（并已实测）

**我此前说错过一次**：把「u2netp 只有 4.6MB」和「isnet-int8 44.2MB」放在一起比，暗示 u2net 档位没有小体积选项。
这不成立 —— **fp32 的 u2net 一样能量化到约 42MB**，我随后把它做出来并测了：

| 制品 | 大小 | 来源/做法 |
|---|---|---|
| `u2net.onnx`（fp32） | 167.8MB | HF 镜像 `tomjackson2023/rembg` |
| `u2net-int8.onnx`（动态量化） | **42.2MB** | 本地 `.tools/ai-spike/quantize.py` 生成 |

保真度（权威样例 1104×1424，同一 `extractSubjectFromAIMask` 后处理 + 同一道可靠度门）：

| 对比 | IoU | 说明 |
|---|---|---|
| u2net-int8 vs u2net-fp32（自身保真） | **0.9921** | 差异全在边界，内部空洞 0 |
| isnet-int8 vs isnet-fp32 | 0.9994 | 量化对 ISNet 几乎无损 |
| u2net-int8 vs isnet-int8 | 0.9873 | 两个模型本身就高度一致 |
| u2netp vs isnet-int8 | 0.979 | u2netp 最小，但边界最差 |

所以当时的正确结论应是：**u2net-int8（42MB）与 isnet-int8（44MB）体积基本相同**，
选谁只看「哪个掩码质量更好」，而不是「u2net 没有小体积版本」。

**这条结论现在已经不改变任何决策**：架构已改为服务端推理（`docs/47`），
用户不再下载任何权重，体积因此完全不再是约束，线上直接跑 **fp32 u2net**（质量更好、无量化开销）。
量化版保留在 `.tools/ai-spike/` 仅作证据，不进入交付物。教训记在这里，避免以后重复这个错误比较。

### 12.2 两条需要你重新拍板的发现

**① 「动态 CDN（§6b）」对本档位不成立**：ISNet-int8 是**我们量化生成的**，公网上不存在这个制品
⇒ 只能**自托管**（放自家静态站/对象存储），不能用公共 CDN。这推翻了 §10 已拍板的 6b，
需要改为「**自托管 44.2MB 模型 + sha256 校验 + 本地缓存**」，并确认部署侧能承载这 44MB
（`public/` 入库会导致仓库 +44MB，通常应放对象存储/CDN 后自行上传）。

**② 「保留接触阴影」与既有缺陷记录冲突**：实测三个候选模型**都会排除**接触阴影（底部灰地面判 0）。
而 docs/39 当初把「**主体下方一团灰影**」明确列为**劣化项**（P0 的观感问题之一）。
⇒ 我建议**改为「排除阴影」**（= 模型默认行为，也**不需要**额外后处理，工作量更小）。
若坚持保留，需要专门的「把接触阴影补回掩码」后处理（属新增算法 + 新增风险）。
