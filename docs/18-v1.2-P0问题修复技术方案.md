## 0. 术语与坐标约定（先读，后文全部引用）

## 2. 根因分析

### 2.1 桌面端根因（4 个独立机制，全部要修）

**R1 · 自动 fit 复位环（缩放失效的直接原因）**

`PreviewCanvas.tsx:119-123` 在 `[pattern.width, pattern.height, contentSize.width, contentSize.height]` 变化后 40ms 无条件执行 `fit()`。当前实现中 canvas 的 CSS 尺寸 = `W·zoom + 2·PADDING`（`PreviewCanvas.tsx:68-69`），而 `.canvas-scroll{overflow:auto}`。于是：

1. 用户滚轮把 `zoom` 放大到超过“刚好容纳”的值 → canvas CSS 尺寸大于查看区 → `.canvas-scroll` 出现滚动条；
2. 滚动条占位使查看区 `clientWidth/clientHeight`（即 `contentSize`）变小 → fit effect 依赖项变化；
3. 40ms 后 `fit()` 把 zoom 拉回适应值、pan 清零 → 滚动条消失 → `contentSize` 回弹 → 再次 fit（幂等，不振荡，但**用户的放大操作被抹掉**）。

网格越大（100/200 格）时 fit 的 zoom 越小（如 200 格在 ~1000px 宽查看区 fit≈4px/格），任何一次放大都立刻越过“内容=查看区”的平衡点触发滚动条，所以表现为**完全无法保持放大态**。小图（29/58 格）因用户放大后内容仍在查看区内或滚动条只出现一个方向、`contentSize` 变化小于触发噪声，现象不明显——这解释了“只有 100/200 格大尺寸失效”。

**R2 · 滚轮缩放无光标锚点（“越滚越跑”）**

`onWheel` 只做 `zoomBy(factor)`（`PreviewCanvas.tsx:326-329`），只改 zoom 不改 pan。按 docs/02 §5 契约“滚轮缩放以光标为锚点”，实现缺锚点数学：放大时鼠标下的网格点随缩放漂移出视野，用户每滚一次都要重新找目标。大网格放大倍数高时漂移量 = 缩放后光标下内容的位移，随 zoom 增大而放大。

**R3 · canvas 位图随全图尺寸×zoom 增长，超浏览器上限（放大后空白）**

绘制 effect（`PreviewCanvas.tsx:83-103`）把 `canvas.width = round((W·zoom+2·PADDING)·dpr)`。对 200×200 网格：`zoom=41、dpr=2` 时位图宽 ≈ 16480px，面积 ≈ 2.72 亿 px²，超过 Chrome 单 canvas 面积上限（≈ 268,435,456 px²）；`zoom=96、dpr=2` 时约 14.9 亿 px²。浏览器对超限赋值的行为是实现相关（通常画布被清空/保持旧尺寸），表现为**放大到阈值后画面空白或不再更新**。此外全图重绘（含 `fillText`）在 4 万格 + 高 zoom 下每帧开销随 zoom 平方增长。

**R4 · 平移缺少可用入口与可见性（“缺失平移功能”）**

- `.canvas-scroll` 内滚动条是唯一的“原生滚动”通道，但 `onWheel` 对一切 wheel 事件 `preventDefault`，滚动条永远无法被滚轮驱动；在内容（canvas）大于查看区时用户**无法用滚轮滚动视野**；
- 平移只靠左键/中键按住拖拽，无光标反馈（无 `grab`）、无快捷键（docs/02 承诺“空格拖拽”未实现）、无提示文案；
- R1 的复位环使拖拽放大态无法维持，用户即使拖拽也会立刻回到 fit，体感=“没有平移”。

**R5 · `MIN_ZOOM=1` 硬下限 + 居中缺失**

`MIN_ZOOM=1`（`PreviewCanvas.tsx:26`）与 `fit()` 的 `Math.floor(scale)` 组合：当查看区短边 < 网格格数时（如手机横屏、或 >387 格方形板），“适应”无法显示全图（zoom 被抬到 1，网格宽 W>查看区 → 只能看到左上局部且不可滚动到右下之外）。旧实现里 canvas 本身随内容变大、靠容器滚动“看全”，视口模型下必须允许 `zoom<1`。

### 2.2 移动端根因（机制）

**M1 · 底栏高度口径不一致（遮挡）**

- `.mobile-nav` 实际盒高 = `58px + env(safe-area-inset-bottom)`（iPhone 有 Home 条时 inset≈34px → 总高≈92px；`mobile-viewer.css:135-148`）；
- `.app-body` 却只预留 `56 + 58`（`mobile-viewer.css:48-53`）。
- 结果：`app-body` 底部约 `env(safe-area-inset-bottom)` 高的区域与固定底栏重叠，被不透明底栏盖住。图纸段表现为 canvas 最底部内容（或 hover 信息条）被遮；统计段表现为表格最后一行被遮。
- 次要：非 iOS（inset=0）时两口径相等，故“桌面 Chromium 模拟不重现”，只有真机/模拟 iOS 才可见 —— 与“移动审查在 Chromium 过、真机反馈残”一致（docs/17 §6 残余风险印证）。

**M2 · 底部工具条单行 flex，窄屏溢出（错位）**

`.preview-mobile-controls` 单行 6 个控件，每按钮 `min-width:48px`、gap 8px、容器 padding 12px：最小需要 `6·48+5·8+12=340px`。iPhone SE 逻辑宽 320、Android 320 均不够；flex 不换行 → 按钮被裁/溢出查看区（视口内 `scrollWidth>innerWidth` 或视觉截断）。同时按钮高度被移动端全局规则统一到 44px，若未来再塞入按钮必然破坏。

**M3 · 层级 z 值无体系**

现散落值：header 20、app-error 19、mobile-nav 30、fullscreen-viewer 60、hover-bar/converting-badge 3（在 `.canvas-scroll` 内）。任何新悬浮层若取值在 20–60 之间即可能与 header/nav/viewer 竞争；全屏查看器只 `display:none`（mobile.css:49-51）而非卸载，`z-index` 若被后续组件超过会造成“底栏盖在全屏之上”类问题。需要一份**层叠序表**与常量。

**M4 · 切段/旋转触发无条件 fit**

fit effect 监听 `contentSize`；手机三段切换（params/preview/stats）与转屏都会改变查看区尺寸 → 用户正在放大查看的视图被重置。根因同 R1 的“fit 触发条件过宽”，移动端无滚动条也会踩中。

**M5 · 溢出兜底不统一**

`body`/`.app-shell` 的 `overflow-x:hidden` 只治标：若子元素宽出（工具条、长 chips、`.stats-summary` 横向、header actions），`scrollWidth>innerWidth` 依然成立；需要每个“必溢元素”有自己的 `min-width:0` + 内部滚动/换行策略，并用断言卡住（docs/14 §4-1 断言在 v1.1 已过，v1.2 加 ≤340 档重验）。

## 3. 修复设计 A —— 视口缩放渲染模型（桌面与移动共用，消灭 R1/R3/R4/R5/M4）

### 3.1 模型与不变量

把“canvas = 网格内容大小”改为 **canvas = 查看区大小（恒定）**，网格内容通过 `(pan, zoom)` 在画布内平移缩放绘制。这与 docs/02 §5 的“单 `<canvas>`、缩放 = 改变画布变换，不做 DOM 网格”完全同向，只是把变换从“canvas 位图随内容涨”收敛为“位图恒定 + 变换 + 可见区裁剪”。

实现后的不变量（每条都写进单测或运行时断言注释）：

- **I1（位图恒定）**：`canvas.width = ceil(查看区宽·dpr)`、`canvas.height = ceil(查看区高·dpr)`，与 `zoom/pan/W/H` 无关。=> 消灭 R3。
- **I2（视图不丢失）**：任何**内容尺寸变化**（ResizeObserver 回调、切段、转屏、滚动条增减）只触发“clamp pan 到新边界 + 必要时重绘”，**不触发 fit**。=> 消灭 R1/M4。
- **I3（fit 触发白名单）**：`fit()` 仅在 ①pattern 更换（`width/height/codes/paletteId` 变化）、②用户点“适应/双击复位”、③由 fit 态产生的布局跳变（见 §3.5）时执行。=> 消灭 R1/M4。
- **I4（可见区裁剪）**：绘制循环只遍历屏幕可见的格子区间，越界格不画。=> 配合 I1 保证帧成本有界（消灭 R3 的性能面）。
- **I5（允许 zoom<1）**：`zoom ∈ [ZOOM_MIN, ZOOM_MAX] = [0.05, 96]`（CSS px/格）；fit 不再 `floor` 后与 1 取 max。=> 消灭 R5。
- **I6（可平移判定）**：网格屏幕尺寸 ≥ 查看区-边距时允许拖拽平移；网格小于查看区时由 `clampPan` 提供“居中且可小幅拖动”区间（§3.4）。=> 支持 R4 修复（视图层让平移永远有效、可见）。

> 外观注意：画布铺满查看区后，`.canvas-scroll` 的点阵底纹会被 `.preview-canvas` 的棋盘纹背景覆盖而不可见。如需保留点阵底纹，可把底纹样式统一移到 `.preview-canvas` 上（棋盘纹随画布铺满即可）——纯外观差异，不影响本方案任何不变量与断言。

### 3.2 新模块与签名（Codex 照此实现，勿改签名）

```ts
// 新增 src/app/viewport.ts —— 纯函数、零 DOM、可单测（与 gesture.ts 同风格）
// 复用 src/app/gesture.ts 的 PADDING / clampPan / PanClamp。

export const ZOOM_MIN = 0.05;            // CSS px/格
export const ZOOM_MAX = 96;              // CSS px/格（不变）
export const FIT_PAD = 16;               // fit 时四周留白（CSS px，沿用现 fit 的 pad=16）

/** 适应缩放：取宽/高两个方向的容纳比例取小，保证整图可见。
 *  raw>=1 时向下取整（避免 1px 溢出）；raw<1 时保留原值（允许 zoom<1 整图可见），
 *  最终夹到 [ZOOM_MIN, ZOOM_MAX]。 */
export function fitZoom(viewW: number, viewH: number, gridW: number, gridH: number): number {
  const sx = (viewW - 2 * FIT_PAD) / Math.max(1, gridW);
  const sy = (viewH - 2 * FIT_PAD) / Math.max(1, gridH);
  const raw = Math.min(sx, sy);
  const z = raw >= 1 ? Math.floor(raw) : raw;
  return Math.max(ZOOM_MIN, Math.min(ZOOM_MAX, z));
}

/** 使“网格中心”对准“查看区中心”的 pan（未 clamp，调用方须再 clamp）。 */
export function centerPan(
  viewW: number, viewH: number, zoom: number, gridW: number, gridH: number
): { panX: number; panY: number } {
  return {
    panX: (viewW - gridW * zoom) / 2 - PADDING,
    panY: (viewH - gridH * zoom) / 2 - PADDING
  };
}

/** 滚轮/捏合缩放锚点：缩放前后，屏幕点 (lx,ly) 下的网格点保持不动。 */
export function zoomAround(
  view: { zoom: number; panX: number; panY: number },
  localX: number, localY: number,      // 相对查看区左上角的 CSS px
  factor: number,
  clampPanFn: (gridCssW: number, gridCssH: number, viewW: number, viewH: number,
               panX: number, panY: number) => { panX: number; panY: number }
): { zoom: number; panX: number; panY: number } {
  const next = Math.max(ZOOM_MIN, Math.min(ZOOM_MAX, view.zoom * factor));
  const wx = (localX - PADDING - view.panX) / Math.max(1e-6, view.zoom); // 网格坐标(浮点,可越界)
  const wy = (localY - PADDING - view.panY) / Math.max(1e-6, view.zoom);
  const panX = localX - PADDING - wx * next;
  const panY = localY - PADDING - wy * next;
  return { zoom: next, panX, panY };
  // clamp 由调用方在拿到“下一帧网格屏幕尺寸”后统一执行（见 §3.4 zoomAfterClamp 用法）。
}

/** 按钮缩放（无锚点事件）：保持当前“查看区中心下的网格点”不动。 */
export function zoomCentered(view: { zoom: number; panX: number; panY: number },
                             viewW: number, viewH: number, factor: number): { zoom: number; panX: number; panY: number } {
  return zoomAround(view, viewW / 2, viewH / 2, factor, () => ({ panX: view.panX, panY: view.panY }));
  // 具体 clamp 见调用方统一路径；此函数只算“中心锚定”后的 pan。
}

/** 可见格子区间（含边界，col1/row1 为开区间）；全不可见时返回空区间。 */
export function visibleCellRange(
  gridW: number, gridH: number,
  offsetX: number, offsetY: number,   // 物理像素（PADDING+pan)*dpr
  cellPx: number,                     // 物理像素/格 = zoom*dpr
  canvasW: number, canvasH: number    // 物理像素
): { col0: number; row0: number; col1: number; row1: number } | null {
  const col0 = Math.max(0, Math.floor(-offsetX / cellPx));
  const col1 = Math.min(gridW, Math.ceil((canvasW - offsetX) / cellPx));
  const row0 = Math.max(0, Math.floor(-offsetY / cellPx));
  const row1 = Math.min(gridH, Math.ceil((canvasH - offsetY) / cellPx));
  if (col0 >= col1 || row0 >= row1) return null;
  return { col0, row0, col1, row1 };
}
```

`PreviewCanvas.tsx` 消费点（行为规格，非逐行 diff）：

1. 移除“canvas CSS 尺寸随内容变化”：`canvas.style.width='100%'; canvas.style.height='100%'`；画布 **CSS 尺寸恒等于查看区**，物理尺寸在 ResizeObserver 回调里按 `ceil(clientWidth·dpr)` 更新（dpr 变化用 `matchMedia('(resolution)')` 或 resize 里重算）。把画布位图分配移出绘制 effect。
2. 绘制 effect 依赖 `[pattern, palette, zoom, panX, panY, showCodes, showGridLines, hover, contentSize, dpr]`：`cellPx=zoom·dpr; offsetX=(PADDING+panX)·dpr; offsetY=…`；`range=visibleCellRange(...)`；调用 `drawGrid(ctx, pattern, palette, {cellPx, offsetX, offsetY, showCodes, showGridLines, hover}, range)`。
3. `hitCellAtClient` / `toggleDoubleZoom` / `updatePinch` 中的坐标公式不变（它们已在“网格屏幕矩形 = PADDING+pan”口径下工作）。
4. **fit 触发策略替换**（§3.5）。

### 3.3 `drawGrid` 增加可选可见区参数


- **导出/打印不变**：`src/export/png.ts`、`src/export/print.ts` 调 `drawGrid` 时**不传 range**，仍全图高分辨率渲染（docs/14 §2 P0-5“导出为全分辨率、非截屏”由离屏 canvas 路径天然保证，视口化只影响屏幕预览）。→ 回归保护点写进 §8。

### 3.4 平移与边界计算逻辑（含居中）

保留 `src/app/gesture.ts` 的 `clampPan`（含测试契约）作为“滚动式”边界：网格 ≥ 查看区时，保证网格至少 `PAN_MARGIN=24` CSS px 留在查看区内（两侧任一）。视口模型下补两条规格：

- **fit/换图/居中**：fit 后 pan = `centerPan(viewW,viewH,zoomFit,W,H)` 再走一次 `clampPan`（fit 状态必然在合法区间内，clamp 为空操作，仅为防御）。
- **clamp 统一出口**：pan（拖拽）、pinch、滚轮锚定、双击放大产生的 pan，全部经同一函数收口：
  ```ts
  const clampView = (next: {zoom:number;panX:number;panY:number}) => {
    const clamped = clampPan(W*next.zoom, H*next.zoom, viewW, viewH, next.panX, next.panY);
    return { zoom: next.zoom, panX: clamped.panX, panY: clamped.panY };
  };
  ```
  （其中 `viewW/viewH` 为查看区 CSS 尺寸 = `contentSize`。）
- **边界语义注记**（写进 clampPan 注释更新）：`clampAxis` 的 `max<min` 分支返回 0 —— 只在“查看区与网格都不足 2·PAN_MARGIN 时”才会出现，属防御；网格≥1、查看区≥48px 时永不触发。补充单测断言该分支。

- **边界极端态（验收要测）**：
  1. `zoom=ZOOM_MAX`、网格 200×200 → pan 合法、画布位图仍 ≤ 查看区×dpr（I1 断言）。
  2. `zoom=ZOOM_MIN`、查看区很小 → 整图可见（I5 断言：fit 后网格屏幕矩形 ⊂ 查看区 ±1px）。
  3. 拖拽 10000px → pan 停在 clamp 边界，网格仍有 ≥24px 可见。
  4. 网格 < 查看区 → fit 后网格居中（中心差 ≤1px）。

### 3.5 fit 触发策略（替换 `PreviewCanvas.tsx:119-123`）

```ts
// 状态：fittedZoomRef 记录“最近一次由 fit 设置的 zoom”。
// 规则：
// 1) pattern 身份变化（width/height/paletteId/codes 引用）→ 40ms 防抖后 fit()；
// 2) contentSize 变化（ResizeObserver）→ 只做：
//      a. 若 |view.zoom - fittedZoomRef| <= 1e-6（用户仍停在 fit 档）→ 重新 fit()（保持“整图可见”承诺）；
//      b. 否则仅 clamp pan（clampView 口径）并重绘，zoom 保持；
// 3) 用户点“适应/双击复位/模式变更的 UI 复位”→ fit()；
// 4) fit() 内部：zoom=fitZoom(...) 后写 fittedZoomRef；pan=centerPan(...) 后 clamp。
// 保证：zoom 被用户改动过的瞬间起，任何后续尺寸变化都不会再重置 zoom。
```

实现时用 ref 记录 `userZoomedRef`（在 wheel/pinch/双击/± 按钮回调里置真，fit 回调里置假）即可得到与上式等价的写法；**二选一实现，行为必须满足 I2/I3 与 §7 断言**。

## 4. 修复设计 B —— 桌面鼠标平移补全（消灭 R4）

在保留“滚轮=缩放、左/中键拖拽=平移”（docs/01 §3.1 P0 契约）的前提下，补齐缺失的平移可用性：

## 6. 边界计算逻辑汇总（Codex 实现时的“数学抽屉”）

| 情形 | 计算 | 出处/断言 |
|---|---|---|
| fit zoom | raw=min((viewW-32)/W,(viewH-32)/H)；raw≥1 取 floor，raw<1 取 raw；夹到 [ZOOM_MIN,ZOOM_MAX] | §3.2 `fitZoom` |
| fit 后 pan | `centerPan(...)` 后过 `clampPan` | §3.4 |
| 滚轮/捏合锚点 | `zoomAround`（缩放前后锚点下网格点不变） | §3.2 |
| 按钮/中心缩放 | `zoomCentered` | §3.2 |
| 拖拽 | `pan = clampPan(W·zoom,H·zoom,viewW,viewH, startPan+Δ)` | 沿用 `clampPan` + `clampView` |
| 可见区 | `visibleCellRange`（物理像素口径） | §3.2 + drawGrid range |
| 命中格 | `floor((cssX-PADDING-panX)/zoom)`，越界返回 null | 不变 |
| 网格可见性下界 | `PAN_MARGIN=24` CSS px；`clampAxis` 的 `max<min` → 0 | gesture.ts 注释更新 |
| 位图尺寸 | `ceil(查看区宽·dpr)×ceil(查看区高·dpr)`，与 zoom 无关 | I1 断言（§7-7） |
| 内容 < 查看区 | 居中显示，拖拽范围 = clamp 区间（可小幅拖动） | §3.4 注记 |

单测规划（新文件 `tests/unit/viewport.test.ts`；`gesture.test.ts` 保留）：

1. `fitZoom` 四向断言：宽约束/高约束/超小查看区（zoom=ZOOM_MIN）/超大网格（zoom 上限）。
2. `centerPan`：fit 后网格屏幕矩形中心 == 查看区中心（±1px）。
3. `zoomAround`：缩放前后同一点下的网格坐标差 <1e-6；连续 10 次 ×1.12 后 zoom==ZOOM_MAX 封顶、pan 单调且 clamp 后网格 ≥24px 可见。
4. `visibleCellRange`：完全在屏/部分越界/整体在左上方/整体不可见(null) 四态。
5. 回归：`clampPan` 既有用例不改仍绿；补 `max<min` 分支用例。

## 10. 下游实现 FAQ（技术疑问与方案调整口径）

**Q1 视口化后导出 PNG 会不会变成截屏？**
不会。`exportPng`/`printSheet` 使用**独立离屏大 canvas** 调 `drawGrid(..., range 缺省=全图)` 全量高分辨率渲染，不经过屏幕 `PreviewCanvas`；本方案只改屏幕预览路径（docs/18 §3.3、§8）。

**Q2 zoom<1（0.05–1）时格线/文字还画吗？**
`drawGrid` 的 LOD 阈值按**物理 cellPx**（=zoom·dpr）判断，zoom<1 时 cellPx<1 远低于 14 → 只画色块，行为与既有 LOD 一致，无需新分支。

**Q3 dpr 变化（跨屏拖动/浏览器缩放）怎么办？**
ResizeObserver 只保证尺寸；dpr 用 `window.devicePixelRatio` 在**绘制 effect 内**读取（已是依赖项），跨屏时容器 resize 或 matchMedia 触发重绘即重算位图。不额外引入监听器（实现时在 effect 依赖里含 dpr 即可）。

**Q4 滚轮高频事件会不会把绘制打满？**
绘制 effect 幂等；每事件一次重绘在可见格裁剪后开销有界。如需合并，可在 `onWheel` 里用 `requestAnimationFrame` 聚合最近一次 view 变更再提交（可选优化，不改变本方案的任何不变量；不做硬性帧率断言，避免 CI 抖动）。

**Q5 `env(safe-area-inset-bottom)` 不支持的旧内核怎么办？**
CSS 变量版规则前先声明一版无 `env()` 的兜底（如 `height:calc(100dvh - 56px - 58px)`），再声明变量版覆盖；不支持 `env()` 时该值为 0px，变量版退化为与兜底一致。

**Q6 捏合/双击/点按的手势数学会改吗？**
不改阈值与“冻结 startZoom/startPan 做锚点”的数学（docs/17 §3.1 已审查）；只把各手势的产物统一走 `clampView` 收口 + 新 fit 触发策略。回归脚本复用 docs/17 的 28 项断言。

**Q7 为什么不用“原生滚动容器”来做平移？**
滚动条与位图随 zoom 增长是 R1/R3 的根源（滚动条占位 → contentSize 变化 → 自动 fit 复位）。视口模型把“滚动”语义收敛为 `(zoom, pan)` 纯变换 + clamp，行为完全确定、可在单测覆盖，滚动条对布局的影响被整体移除。

**Q8 全屏查看器与预览复用同一组件，改动会不会互相影响？**
不会产生分叉：全屏只是把 `PreviewCanvas` 挂到 `.fullscreen-viewer` 容器里，容器尺寸即其查看区；所有数学按“自身查看区”计算，与是否全屏无关。断言 4/10 分别覆盖两处。
